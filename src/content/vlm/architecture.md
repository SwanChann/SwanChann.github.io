## 这一页回答什么

继续使用[基础章](../foundations/)的照片：一只戴红项圈的小猫坐在沙发上。用户问：**“这只猫的项圈是什么颜色？”**

我们用一个“ViT 视觉编码器 + 投影连接器 + 语言模型”的教学系统，逐步追踪信息。它类似一些生成式 VLM 使用的结构，**不代表每个模型都有相同模块**。下面所有尺寸、向量维度和输出都是演示设定，不是某个实际模型的配置或实验结果。

先记住两个词：**向量**是一组有顺序的数值；**特征序列**是按一定顺序放在一起的多个特征向量。你不必先知道这些数值的具体值，理解它们来自哪里、交给谁即可。

## 第一步：读取像素，再做预处理

### 程序读取的不是“猫”，而是颜色数值

假设原图是 1024 × 768 的 RGB 图片。解码后，每个位置有三个颜色数值，组成一个 `768 × 1024 × 3` 的数组。这个数组里没有额外一列写着“项圈是红色”。

预处理程序根据模型输入约定，可能缩放、裁剪、补边，并把像素值转换到模型使用的数值范围。例如把 0–255 的整数转换成浮点数，再根据既定均值和标准差做归一化。**归一化**在这里是调整数值尺度；它本身不识别猫。

### 为什么预处理会影响最终答案

教学中先假设将整张图缩放成 224 × 224。猫的红项圈本来只占很小区域，缩小后可能只有几个像素；若采用裁剪，还可能直接丢掉相关区域。后面的编码器只能处理实际收到的内容。

这解释了“预处理需保留细节”是什么意思：不是让程序先认出项圈，而是确保原图中的相关像素没有在尺寸调整或裁剪中被丢失到不可辨认。实际缩放与裁剪规则因模型而异，不能只看原始图片尺寸判断模型收到多少细节。

**这一阶段的输入与输出：原图像素数组 → 调整后的像素数组。** 此时还没有答案，也没有自然语言描述。

## 第二步：视觉编码器计算特征

### 把图片切成图块，不是切成物体

在这个 ViT 示例中，将 224 × 224 的图片分成 16 × 16 的图块，会得到 196 个图块。一个图块有 `16 × 16 × 3 = 768` 个像素数值。

图块按网格切分，不会自动沿猫的轮廓切。一块可能包含半只耳朵和背景，项圈也可能跨越多块。模型需要根据图块之间的关系处理这些信息。

### 将图块像素变成向量

每块的像素数值通过可学习的计算，变成一个固定长度的向量。假设本例每块输出 768 维，也就是 768 个数。这里输入像素数与输出维度恰好相同，**只是示例巧合，实际投影完全可以改变维度**。

为了让模型区分图块位置，还会加入位置相关信息；否则仅有图块内容无法直接表示哪个在左、哪个在右。具体位置编码设计因模型而异。

随后，多个 Transformer 层处理这些图块向量。这里的 **attention（注意力）**是一种让一个位置的计算结合其他位置信息的机制，例如处理项圈区域时，可以结合猫的身体区域和周围场景。它是一套数值计算，不能仅凭注意力图认定模型具有人的注视过程或已经认出项圈。

### 编码器最终输出什么

假设本例保留 196 个图块位置，每个位置有一个 768 维特征向量，则输出形状是 `196 × 768`。可以把它理解为一张表：196 行，每行 768 个数。

这就是一种**特征序列**。行里通常不是“猫、沙发、红色”这样的词，而是模型学到的数值表示。经过全局信息交互后，一行也可能包含其他区域的信息，不能把它当成独立图块的完整说明书。

有些模型会增加汇总位置、保留不同层的特征或压缩序列；本例省略这些变化。原始 ViT 的图块与 Transformer 设计见[ViT 论文](https://arxiv.org/abs/2010.11929)。

### 如果视觉编码器是 CNN 呢

CNN 往往生成带空间排列的 **feature map（特征图）**：可以想成每个网格位置存放一组特征数值的表。为了交给后续模块，这种空间网格也可以整理成向量序列。

因此，无论采用 CNN 还是 ViT，先抓住共同功能：**从像素计算可供后续任务使用的视觉特征**。它通常不是一个直接输出“红项圈”的对象列表。

## 第三步：理解“视觉 token”究竟是什么

在上述序列中，一个特征位置常被称为一个 **visual token（视觉 token）**。本例有 196 个位置，也可以说有 196 个视觉 token。其他模型的 token 可能来自压缩、合并或查询结果，不一定与原始图块一一对应。

要把三个概念分开：

| 概念 | 猫图例子中是什么 |
|---|---|
| Pixel，像素 | 输入图片某个位置的 RGB 数值 |
| Patch，图块 | 网格划分出的一块原始图像区域 |
| Visual token，视觉 token | 经过计算后，供模型处理的一个视觉向量位置 |

**文本 token**通常先是词表中的离散编号，然后转成 embedding 向量；这里的视觉 token 通常直接是连续特征向量。它们都能以向量形式参加后续计算，但视觉 token 不需要先转换成一个汉字或一个词。

“连续向量”中的连续，是说各维度可取浮点数值，不是说模型在连续播放图片。

## 第四步：连接器怎样把特征交给 LLM

### 为什么需要一个连接部分

假设视觉编码器每个位置输出 768 个数，而语言模型内部每个输入位置使用 4096 个数。前者不能按这个接口直接送入后者。除此之外，即使维度相同，也不代表语言模型已经学会解释视觉特征的含义。

一个 **projector（投影器）**可以把每个 768 维向量经过学到的计算变成 4096 维向量。于是 `196 × 768` 变成 `196 × 4096`：位置数不变，每个位置的数值形式改变。这类似把两个模块的数值接口接通，但并不是把图片逐字翻译成一句中文。

在线性投影的例子里，输出向量的第一个数，可以由输入的 768 个数分别乘上可学习的权重、求和，再加一个偏置得到。换另一组权重，得到第二个数；如此得到 4096 个输出数。**所谓“映射”，首先就是这样的数值运算**，这些权重需要训练，不是人工规定某一维代表“红色”。

### 投影为什么能够学到有用联系

投影器的参数通过训练调整。训练时，猫图、问题和期望答案之间的误差可以为允许更新的参数提供学习信号。这样，投影器逐渐产生更有助于下游任务的输出。哪些模块冻结、哪些更新，是具体训练方案的选择，见[训练](../training/)。

如果只是随机初始化一个投影器，就算输入输出尺寸完全匹配，也不能期待它立刻准确回答图像问题。**维度兼容解决了接入形式，训练还要解决怎样利用。**

### Connector 是大类，projector 只是其中一种

| 连接方式 | 对本例特征可以做什么 | 第一次阅读要理解的差别 |
|---|---|---|
| 线性投影 | 对每个位置做一次学到的线性变换 | 可以改变维度，不一定改变 token 数 |
| MLP，多层感知机 | 做多层变换，中间加入非线性计算 | 映射更灵活，也不一定压缩位置数 |
| Q-Former | 用可学习的查询向量从视觉特征中获取信息 | 可以把很多视觉位置汇聚为较少的输出位置 |
| Resampler 一类模块 | 将长度可变或较长的视觉序列整理为另一组向量 | 常用于控制交给后续模型的 token 数 |

**查询向量**可以先理解为模型学到的一组读取请求：它们通过注意力获取视觉特征，而不是用户写出的文字问题，也不是人工指定的“第一个查询找猫，第二个找红色”。[BLIP-2](https://arxiv.org/abs/2301.12597)给出了 Q-Former 连接冻结视觉编码器和语言模型的代表性方案。[LLaVA](https://arxiv.org/abs/2304.08485)展示了视觉投影与指令训练的另一种方案。

如果把 196 个位置压成较少位置，后续计算可能更省，但信息是否充分保留要靠实验判断。不能将所有 connector 都理解成压缩器，也不能仅凭模块名称断言哪一个更好。

## 第五步：问题文字与视觉特征共同参与计算

### 问题也要变成数值

“这只猫的项圈是什么颜色？”先经过 tokenizer（分词器）变成文本 token 编号，再映射成语言模型使用的向量。此时视觉信息和问题信息都已成为数值形式。

在一种常见的**拼接融合**方案中，模型输入可包含一段视觉向量位置和一段问题向量位置。实际序列还会有系统提示、图像标记等格式，本例省略这些细节：

```text
输入序列 = [视觉向量 1, …, 视觉向量 196,
            问题文字向量 1, …, 问题文字向量 N]
```

这里的 N 由分词结果决定。图像位置并没有被替换成“红色项圈”这几个字。

### “融合”具体发生了什么

模型的后续计算可以让文字相关位置结合视觉位置的信息。它学到的参数决定如何处理“项圈”“颜色”等问题线索以及视觉输入，最终影响答案的 token 分数。

这就是“结合图片和问题”的计算含义。它不要求内部真的存在“先找项圈、再读颜色、再造句”三个独立程序。我们可以按这三步诊断任务，但那是研究者的分析方式，不能直接当成模型内部的真实执行记录。

另一类架构使用 **cross-attention（跨注意力）**：文字处理中的某些计算去读取单独保存的视觉特征，而不只是把两者直接拼成一个输入序列。更多统一或交错方案见[前沿方向](../frontiers/)。第一次阅读只需要知道，**融合回答的是图像信息何时、通过什么计算参与语言处理**。

## 第六步：逐个 token 生成答案

在常见的自回归生成方式中，模型根据图像、问题和已生成的文字，计算下一个文本 token 的分数，再通过解码规则选择一个 token。如此反复，直至输出结束。

我们最终可能读到“它戴着红色项圈”。实际 token 切分未必恰好是“它 / 戴着 / 红色 / 项圈”，所以这里不将汉字或词数当 token 数。

**这一阶段产生的是文字答案。** 它受视觉信息、文字上下文和训练学到的语言规律共同影响。生成了“红色”不等于我们已经证明模型准确提取了颜色证据；如果改成蓝项圈后仍回答红色，就需要进一步检查。

## 把整条链重新看一遍

只有理解各步之后，这张表才有用。你现在应当能解释每个箭头前后的东西为什么不同。

| 环节 | 本例的输入 | 本例的输出 | 对颜色问题的作用 |
|---|---|---|---|
| 解码与预处理 | 图片文件与原始像素 | 调整后的像素数组 | 保留足够可用的项圈像素 |
| 视觉编码器 | 像素数组 | 196 个视觉特征向量 | 计算可能携带颜色、形状和位置的信息 |
| 投影连接器 | 每位置 768 维特征 | 每位置 4096 维特征 | 转成后续语言模型可接收并学习利用的形式 |
| 文字处理与融合 | 视觉向量和问题向量 | 结合两种输入的内部表示 | 让问题与视觉证据共同影响后续计算 |
| 语言生成 | 输入上下文与已生成内容 | 逐步生成的文字答案 | 输出颜色判断和句子 |

这条链中，“红色”是答案词，像素里的 RGB 是输入值，视觉特征是中间数值表示。它们之间存在学习到的联系，但不是同一类东西。

## 如果图片更大、项圈更小，会发生什么

固定缩小整图会让小细节更难辨认。保留更多像素是一种办法，但在图块大小不变时，图像越大，图块与视觉 token 就越多，计算和上下文开销通常也会增加。

常见输入处理方法可以用猫图直接理解：

| 方法 | 怎么处理这张猫图 | 要检查的代价或风险 |
|---|---|---|
| 提高分辨率 | 用更大的整图输入保留项圈细节 | 更多计算，模型是否支持该输入设置 |
| Tiling，切片 | 将大图分成多块分别编码，可能再加整图视图 | 局部信息更清楚，但跨块关系需要保留 |
| Crop，裁剪 | 从原图取出猫颈部区域再编码 | 区域选错会丢证据，局部图可能失去上下文 |
| Multi-scale，多尺度 | 同时提供较小整图和较大局部图 | 多份输入之间如何对应，增加多少 token |
| 动态分辨率 | 按图片尺寸和预算使用不同输入大小 | 实际保留多少像素与 token，不能只看宣传名称 |

如果原始细节已经在第一次缩小中丢失，再放大那张低分辨率图不能还原原图的真实细节。重新读取原始高分辨率区域，才可能提供新的视觉证据。放大生成的细节也不能自动当作真值。

[Qwen2.5-VL 技术报告](https://arxiv.org/abs/2502.13923)提供了动态分辨率设计的案例。[MM1](https://arxiv.org/abs/2403.09611)研究了分辨率、视觉 token 等组件因素；其消融结果有特定模型和训练条件，不能据此给所有架构排永久名次。

## 同一个错误，可能来自不同环节

假设模型把红项圈说成蓝色，我们至少有这些候选解释：缩放让项圈难以辨认；视觉特征没有保留足够颜色信息；后续连接或融合未有效利用相关信息；模型回答了另一对象的颜色；生成受到上下文中“蓝色”的影响。

它们目前都是**待检查的解释**。可以尝试提供原图局部裁剪、明确目标、改变项圈颜色或提供正确文字事实来观察结果，但某次干预有效，不能直接证明唯一原因。比如裁剪还改变了背景和目标大小。

这里才是“证据传递链”对研究有用的地方：它帮助我们提出可区分的候选原因。它不是凭最终答案就能逐层读出错误的工具。只有 API 的模型通常更难验证内部模块；未公开的结构不能猜测。

## 学完应能作出的判断

1. **图片通常不会先变成一句完整描述再交给 LLM。** 这类示例中，进入语言处理的是视觉向量；另有系统确实使用 OCR 或文字描述工具，要看实际流程。
2. **特征维度和 token 数不同。** 196 个 token 是 196 个位置，768 维是每个位置的数值数量；二者不能互换。
3. **有图像输入、接口尺寸匹配、能正确使用证据，是三个需要分别检查的条件。** 连接器接通输入，训练塑造利用方式，评测检查任务表现。
4. **更大的语言模型不能保证修复已经丢掉的像素细节。** 要同时检查原图、预处理、编码、训练和推理设置。

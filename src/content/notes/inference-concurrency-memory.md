本地推理的并发成本取决于服务进程、模型副本与请求缓存。每增加一个请求，并不必然重新加载一整份模型权重。

## 先区分请求和副本

同一个推理服务可以让多个请求共享已加载的权重，同时分别维护请求状态。若启动多个独立进程、各加载一份模型，则通常会重复占用权重显存；张量并行等部署还会改变权重在设备间的分布。

因此，“开四个对话”与“起四个模型实例”不是同一种资源使用方式。应先画清楚客户端、服务进程、模型副本与 GPU 的关系。

## 显存不只有参数

对于常见自回归 Transformer 服务，可以用下式做粗略拆分：

```text
总显存 ≈ 权重 + 活跃请求的 KV 缓存 + 激活/临时工作区 + 运行时开销
```

权重部分受参数量、数值精度和量化方式影响；KV 缓存保存历史 token 的注意力键和值，与序列长度、层数、KV 头数和活跃序列数量有关。图像输入的 token 化方式也可能显著改变请求规模。只用“参数量乘每参数字节数”不能得到完整服务需求。

[PagedAttention / vLLM 论文](https://arxiv.org/abs/2309.06180) 针对动态 KV 缓存的碎片和重复存储问题提出内存管理方法。它说明服务调度与缓存组织会影响可容纳批量，但不会让长上下文的资源消耗消失。

## 吞吐提高，不代表每个请求更快

批处理可以提高硬件利用率；并发继续增加，也可能让排队时间变长。需要分别看每秒完成量、首 token 延迟、生成阶段速度和高分位延迟。对一个等待机器人动作的请求而言，平均吞吐不是唯一重要指标。

测量时固定模型版本、精度、输入长度分布和输出上限，再逐步提高并发。记录峰值显存、失败率、排队时间及延迟分布。若只在短问题上测试，不能推断长图文输入也能维持相同并发。

本文没有提供某张显卡能同时服务多少请求的实测结论。设备规划应从真实负载的小规模测量出发，相关接口检查见[模型部署契约](../model-deployment-contracts/)。
